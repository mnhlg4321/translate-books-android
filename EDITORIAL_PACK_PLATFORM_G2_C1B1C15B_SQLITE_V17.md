## Approved decisions implemented

- Project identity requires an explicit stable semantic key and a versioned
  project-definition contract. It is never inferred from `editorial_projects.id`,
  pack/import IDs, random UUIDs, output URI/path, timestamps, UI state or row ID.
  The v1 projection carries canonical projection version, project semantic key,
  project-definition contract version, optional semantic project type,
  scope-policy fingerprint and workflow-policy fingerprint.
- Scope keys use strict UTF-8, Unicode NFC, outer ASCII-whitespace trim,
  nonempty/control rejection, no locale case folding, and preservation of case,
  punctuation and leading numeric meaning such as `001`.
- Required input roles come from an explicit reviewed role contract. Every entry
  has role, ordinal, lowercase SHA-256, byte count and item count. Unknown
  ordinal/count is missing and fails closed; explicit zero remains distinct from
  unknown.
- Closed-run attempt ordinals are allocated by the DAO in a serialized SQLite
  transaction. The caller supplies no authoritative ordinal. The allocation key
  includes scope, run kind, phase and the trusted semantic context.
- All five new tables use `ON DELETE RESTRICT`, no cascade, and before-update /
  before-delete rejection triggers. Nullable source row IDs are provenance only
  and are excluded from identity projections. No provenance detach API exists.
- A closed-run context is accepted only for trusted `DATA_COMPATIBLE` evidence
  whose profile, machine, pack/evaluator contract, schema and fingerprints match
  the immutable evidence rows. `LEGACY_UNATTESTED`, `BLOCKED`, `INVALID`,
  `ENGINE_UPGRADE_REQUIRED`, `ADAPTER_REQUIRED`, stale and mismatched contexts
  fail closed. The current production profile remains non-executable; positive
  device fixtures are test-only trusted contexts.
- Lineage append/readback and v17 binding use one application-owned SQLite
  transaction. No nested independent DAO transaction is used and no raw
  connection is exposed outside the package boundary.

## Canonical projections and domains

The four identity families are generated by the models; callers cannot provide
precomputed identity values. Canonical JSON is deterministic and strict UTF-8.
Set-like role values are sorted deterministically and manifest entries are sorted
by `(role, ordinal)`. Timestamp, row ID, URI/path, UI state and insertion order
are excluded. A semantic byte change changes the relevant fingerprint/identity.

| Family | Identity domain | Stored semantic projection |
|---|---|---|
| Project revision | `EDITORIAL_PROJECT_REVISION_IDENTITY_V1` | Canonical projection version, explicit project key, definition contract version, optional semantic type, scope-policy and workflow-policy fingerprints |
| Input scope snapshot | `EDITORIAL_INPUT_SCOPE_IDENTITY_V1` | Project revision identity, scope canonical version/key, required-role canonical contract/fingerprint, manifest version/fingerprint |
| Closed run context | `EDITORIAL_CLOSED_RUN_IDENTITY_V1` | Project revision, scope snapshot, pack/evaluation/trusted profile context, contract/schema facts, run kind/phase and DAO-allocated attempt ordinal |
| Run-lineage binding | `EDITORIAL_RUN_LINEAGE_BINDING_IDENTITY_V1` | Binding contract version, closed-run identity, lineage record identity and exact lineage record fingerprint |

Separate fingerprint domains are used:
`EDITORIAL_PROJECT_REVISION_FINGERPRINT_V1`,
`EDITORIAL_INPUT_SCOPE_REQUIRED_ROLES_FINGERPRINT_V1`,
`EDITORIAL_INPUT_SCOPE_MANIFEST_FINGERPRINT_V1`,

`EDITORIAL_RUN_LINEAGE_BINDING_FINGERPRINT_V1`.

## Actual SQLite v17 schema

`TranslationRepository.VER` is `17`. `onCreate` creates the v17 tables after
the v16 lineage tables. `onUpgrade` calls only additive
`EditorialMigrationSpec.from16To17()` when `oldVersion < 17`. The migration
contains exactly five `CREATE TABLE IF NOT EXISTS` statements, lookup indexes
and ten immutable update/delete triggers.

### `editorial_project_revisions`

Stores `revision_identity` (lowercase 64-hex primary key),
`revision_canonical_version`, explicit `project_semantic_key`,
`project_definition_contract_version`, optional `semantic_project_type`,
`scope_policy_fingerprint`, `workflow_policy_fingerprint`,
`project_definition_fingerprint` (unique), canonical project projection,
nullable `source_project_row_id` and nonnegative `created_at`. The source FK is
`editorial_projects(id) ON DELETE RESTRICT`.

### `editorial_input_scope_snapshots`

Stores `scope_snapshot_identity` (lowercase 64-hex primary key), project
revision FK, scope canonical version/key, required-role canonical JSON and
fingerprint, manifest version/fingerprint, nullable source chapter row and
nonnegative creation time. The canonical tuple
`(project_revision_identity, canonical_scope_key, manifest_fingerprint)` is
unique and all FKs are restricted.

### `editorial_input_scope_snapshot_entries`

Stores scope snapshot FK, `role`, nonnegative `ordinal`, lowercase
`input_sha256`, nonnegative `byte_count` and nonnegative `item_count`. Primary
key is `(scope_snapshot_identity, role, ordinal)`. Entries cannot exist without
their complete parent snapshot.

### `editorial_closed_run_contexts`

Stores closed-run identity/fingerprint, context version, project revision and
scope snapshot FKs, canonical pack hash, compatibility evaluation ID/outcome,
trusted profile ID/version/hash, machine fingerprint, pack contract ID/version,
pack schema ID/version, evaluator contract version, adapter-set/capability/
compatibility-context fingerprints, engine version, run kind, phase identity,
allocated `run_attempt_ordinal`, input-manifest fingerprint, nullable source run
row and nonnegative `closed_at`. The table has a unique allocation tuple that
includes scope, run kind, phase, pack/evaluation/trusted context and ordinal.
Only immutable closed contexts are stored; there is no OPEN row to update.

### `editorial_run_lineage_bindings`

Stores binding identity, closed-run FK, v16 lineage-record FK, exact lineage
record fingerprint, binding contract version and nonnegative `bound_at`. A
closed run can bind to one lineage record and a lineage record can bind to one
closed run. Exact tuple/idempotent readback is supported; rebind/detach is not.

Every new table has lowercase 64-hex checks for identity/hash fields, nonempty
semantic-field checks, nonnegative ordinal/count/timestamp checks, restricted
foreign keys and update/delete rejection triggers. There is no `ALTER TABLE`,
rebuild, cascade, `INSERT OR REPLACE` or migration-time insert/backfill.

## DAO and result vocabulary

Implemented append/read-only boundaries:

- `EditorialProjectRevisionDao`: append, find by identity, list by semantic key.
- `EditorialInputScopeSnapshotDao`: atomic append of snapshot plus every entry,
  find by identity and list by project revision.
- `EditorialClosedRunContextDao`: append from a draft without caller ordinal,
  find by identity and list by scope; cross-row validation reads the project
  revision, exact scope/manifest, pack and compatibility evaluation.
- `EditorialRunLineageBindingDao`: append, find by identity/closed run/lineage
  identity, and package-private transaction-scoped append.
- `EditorialLineageAndBindingTransactionService`: one shared SQLite transaction
  for v16 lineage append, exact fingerprint readback, and v17 binding.

Stable v17 result codes are:

detach, certify, activate, project-bind or execute API is exposed.

## Attempt allocation and retention

`EditorialClosedRunContextDraft` intentionally has no ordinal. In one SQLite
transaction the DAO first finds an exact existing draft for idempotency, then
serializes allocation over the full scope/run-kind/phase/trusted-context key and
uses the next nonnegative ordinal. A racing duplicate therefore produces one
row/ordinal; the losing request reads back the exact existing immutable context.

All semantic evidence is retained. Restricted provenance FKs prevent a referenced
mutable project/chapter/run/evaluation/lineage row from being deleted. The
existing UI delete flow is not wired to these stores in this phase; C2 must
address the resulting fail-closed retention behavior before production creator
integration. No provenance detach policy was introduced.

## Shared transaction behavior

The transaction service opens one `SQLiteDatabase` transaction, calls the
transaction-scoped v16 lineage append, requires `APPENDED` or exact
`ALREADY_EXISTS`, reads back the exact lineage fingerprint, then appends the v17
binding. It commits only when both are successful/idempotent. A newly appended
lineage plus failed binding rolls back both. A pre-existing lineage plus failed
binding leaves the existing lineage and creates no binding. Same closed run with
different lineage, same lineage with different run, or fingerprint mismatch
fails closed without update/rebind.
